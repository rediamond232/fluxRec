# Fluxrec UX Contract

## Product context

- **Audience:** Linux desktop users recording a Wayland output while checking capture, encode, mux, and queue health.
- **Primary jobs:** Start a hardware encoded recording, stop it cleanly, inspect pipeline and audio telemetry, mix available audio sources, control replay history during a recording, and save retained replay history.
- **Target market(s):** Desktop Linux; no geography-specific workflow is specified.
- **Active locales:** English for the initial Qt application.
- **Language/content register:** Plain English, direct action labels, technical diagnostics available separately from short recovery guidance.
- **Timezone/calendar policy:** Display no ambiguous event timestamps in the initial shell. Output filenames use the workstation's local date and time.
- **Accessibility target:** WCAG 2.2 AA principles adapted to native Qt: keyboard access, visible focus, readable contrast, names for icon buttons, and text alongside color status.

Scenes are local capture profiles, not a compositor. Each profile contains exactly one Wayland output name. The dock lists, selects, adds, renames, and removes profiles and edits the selected output; the name is passed to the recorder on the next session. On the Qt Wayland platform, a refreshable picker lists `QScreen` output names and marks a saved name unavailable when absent. The host's `DP-1` name matched Hyprland's output name in a live read-only check. Manual entry remains available for an unset or unavailable name and on platforms where Qt cannot verify Wayland output names. The recorder confirms the exact name at startup. Scene selection and edits, including the selected output field in Settings, are disabled while a recording or replay-only session is starting, active, or stopping. Other Settings changes apply to the next session. There is always at least one saved scene.

## Engine and telemetry states

The process backend is separate from all widgets. The product is one `fluxrec` binary. With no engine flag it opens the Qt shell; `fluxrec --engine` and the `fluxrec-record` name run the recorder. The shell launches that same binary with argument arrays, never a shell command, and prepends `--engine` when the selected executable is itself. A blank recorder path means this program. An explicit path can still point at another recorder executable.

Settings saves the encoder backend in `recording/encoderBackend` (`vulkan`, `nvenc`, or `experimental-cuda-egl`), defaulting to NVIDIA NVENC for fresh settings. Existing saved choices remain selected. Vulkan Video remains selectable. Direct CUDA EGL is an experimental application-level GPU path. The UI must not describe it as allocation-level zero-copy. While it is selected, unsupported controls are disabled or block saving: output size other than native or 2560×1440, B-frames, NVENC presets, GPU preview, and the frame-identity digest. Constant QP stays selectable. The launch passes `--qp N` without a bitrate argument. That direct-path constant-QP mode has not been live-checked; the earlier H.264 QP 28 color-chart result used the other encoder path. Its pool is 3–16 and its async depth is 1–16, saved separately from the other backends. Five-second motion-1 checks skipped source IDs with pools of 4 and 8 while `capture_dropped` stayed 0; `capture_unarmed` counts a failed arm of the next frame. The default 16-buffer pool stayed exact on matched runs, including one whose high-water reached 16/16. The settings pool note states that. H.264 uses CAVLC; HEVC Main is available with the existing experimental-HEVC acknowledgement. The choice applies to standard recording and replay-only capture on the next session, and the recorder receives `--backend` for both. The toolbar names the selected backend. The signal rail stays WAYLAND › VULKAN › NVENC › MATROSKA with the two-pass conversion note for NVENC and Vulkan Video. Direct CUDA EGL changes that rail to WAYLAND › EGL › NVENC › MATROSKA, labels the route “Direct CUDA EGL,” and replaces the preview with an explicit unused state. That state is not a failed preview and is not allocation-level zero-copy. NVENC requires compatible NVIDIA hardware and an FFmpeg runtime; selecting it does not claim the runtime is available. A startup or runtime failure remains visible in the status and engine log.

GPU frame identity verification is an opt-in diagnostic saved in `recording/verifyFrameIds`, defaulting off. When enabled, the UI passes `--verify-frame-ids` for standard and replay-only capture. It hashes each captured RGB frame on the GPU, reads back a 16-byte digest, and writes a stderr record per completed digest. This adds GPU work and synchronization and may reduce recording FPS. At 2560 × 1440 and 360 FPS, the estimated source-image read traffic is about 5.3 GB/s; this is a calculated traffic estimate, not a measured throughput cost. Statistics shows unique and duplicated frames plus checked, skipped, and unclassified digest counts. Missing counters remain “Not reported”; zero is shown only when the recorder reports a zero.

| State | Entry evidence | Main action | User-visible meaning |
|---|---|---|---|
| Engine unavailable | Configured executable cannot be found/executed | Open Settings | Recording cannot start until an executable is located |
| Engine available | Executable path exists and can be launched | Start recording | Engine is ready to be launched; no live connection is implied |
| Starting | `QProcess` start event pending | None | Recorder startup is in progress |
| Recording | Recorder process has started | Stop recording | A recorder process is active; final file size is not final yet |
| Stopping | SIGINT sent to the recorder process | None | Wait for the engine to flush and close Matroska |
| Failed | Process start/runtime/exit failure | Retry or inspect log | The active operation did not complete successfully |

Only engine JSONL reports populate statistics. `null`, missing, non-finite, or malformed values show as “Not reported”; zero is a real reported zero. Preserve the last valid snapshot and identify it as stale when its age exceeds three seconds. Never interpolate, invent 360 FPS, or infer unique FPS from ordinary capture FPS.

The telemetry view exposes delivered capture, Wayland completion, admitted, intentionally rate-limited, distinct capture presentation-time, unique, duplicated, identity-checked, identity-skipped, identity-unclassified, submitted, encoded, and muxed frame counts; stage drop counts, including replay append/router drops; capture, GPU conversion, NVENC, mux, and disk-write timing distributions; and separately labeled CPU host spans for DMA-BUF import, Vulkan-to-CUDA transfer, filter submit/pull, encoder send/receive, and submit-to-packet wall time. CPU host spans are not presented as GPU execution duration. It also shows frame-pool and queue occupancy/high-water/capacity; output file size and bitrate; replay payload size; and recorder/GPU/NVENC utilization when reported. The Average FPS tab divides cumulative captured, unique, encoded, and muxed counts by the span from one second before the first report through the last report received while capture is still running. Reports received after Stop are omitted, so the second in which recording stops does not lower that average. The readings above the tabs remain the latest one-second interval. Unique average stays “Not reported” unless unique frames are reported. `replay.packet_queue_drops` is distinct from mux drops. Unsupported or unobserved values remain “Not reported.” Identity coverage remains unreported when GPU frame identity verification is off.

Replay history duration is configured before launch. The UI gates Start/Stop/Save from the recorder's `replay.enabled` and `replay.active` telemetry and waits for typed command acknowledgements. Starting a stopped ring begins a fresh history generation; stopping freezes appends but retains the existing history for Save Replay. Saving remains available when an enabled ring is stopped. `storage.replay_budget_bytes` is a budget reading and does not determine whether a ring exists.

When the recorder is idle and replay history is configured, Start replay-only session launches capture without a primary output file. Its `recording_mode` telemetry is `replay_only`; it creates no primary MKV file or primary mux. The Controls dock identifies this mode and changes Stop recording to Stop replay-only session. Stop sends the recorder's `stop` control line and waits for orderly shutdown (SIGINT is the fallback). A replay-only exit is considered successful from the process result and orderly shutdown alone; the UI does not require a primary output file. Primary output and mux readings say “Not used” in this mode. Replay drops remain separate at `frames.dropped_by_stage.replay` and `replay.packet_queue_drops`; they are never shown as mux drops.

Audio capture is off until Settings “Capture audio tracks” is enabled. The mixer holds up to eight tracks. Each chooses an input and an optional monitor output. An unsaved list captures the default desktop monitor and the default microphone, with no monitor playback; the recorder selects that pair with `--audio-tracks default`. A saved empty list captures no audio. Device edits apply to the next session and are disabled while a session is busy. When enabled, configured tracks are captured during standard recording and retained in replay history during replay-only capture. The mixer uses only `audio.tracks` telemetry and typed control acknowledgements; missing values stay “Not reported,” and the panel never simulates levels. Gain is linear from 0.00× to 4.00×. Gain and mute wait for a streaming track and an acknowledgement. Control labels update after acknowledgement. Monitor playback is not a recorded track. A failed monitor does not fail the session. A failed input fails startup, and the error includes the track name. Audio freshness follows the same three-second stale threshold as the rest of telemetry.

The GOP/keyframe interval is passed to the recorder as `--gop`, measured in frames, and editable from 1 to 3600. Its current default is 120 frames; because capture FPS is engine-defined, the UI does not convert that count into an exact duration. The GPU capture pool defaults to 48 buffers and remains editable from 2 to 64. One current motion test observed zero missed frame IDs at 48; this is a measured starting point, not a universal optimum. Larger pools reserve more GPU memory and may add queueing latency.

The encoder async-depth control is labeled for the currently selected backend and accepts 1–64 frames. Settings saves Vulkan Video depth as `recording/asyncDepth` (default 8) and NVENC depth as `recording/nvencAsyncDepth` (default 4). Switching backends restores that backend's saved depth, so editing one does not overwrite the other. NVENC preset is saved as `recording/nvencPreset`, defaults to `p1`, and offers `p1` through `p7`; the control is hidden and disabled with Vulkan Video selected. NVENC B-frame count is saved as `recording/nvencBFrames`, defaults to 0, and accepts 0–4; it is visible and enabled only for NVENC. The process adapter passes the selected backend and its async depth, plus the NVENC preset and B-frame count when NVENC is selected, for both standard recording and replay-only launch. Vulkan omits the B-frame argument, and the CLI rejects nonzero B-frames for Vulkan Video. The GOP must be at least the B-frame count plus two frames. Zero keeps the low-latency I/P-only mode. Nonzero counts disable the explicit NVENC low-latency and zero-reorder flags and add frame reordering. H.264 and HEVC NVENC each passed a 60-second source-ID check at depth 4 with a 48-buffer pool and synchronized scale, but those checks used zero B-frames. Controlled H.264 and HEVC runs at depth 8 produced periodic black output; the UI recommends depth 4 for normal recordings. Separate high-motion NVENC runs also passed: H.264 QP 40 produced 21,600 consecutive IDs in 60 seconds, with pool high-water 41 of 48; HEVC produced 21,599 consecutive IDs in 60 seconds. A bounded 20-second H.264 NVENC capture in a fullscreen Minecraft practice world saved 7,201 frames at about 360 FPS; a separate digest run classified all 7,201 adjacent images as unique. CS2, sustained headroom in more demanding games, alternate presets, and other hardware/configurations remain unvalidated. CPU replay-export coverage exercises reordered H.264 packets with separate PTS/DTS and synchronized audio. A live eight-second H.264 NVENC B-frame-2 recording and replay export each saved consecutive numbered source IDs with two AAC tracks. A twelve-second HEVC B-frame-2 recording decoded correctly but filled the frame pool and missed source IDs at about 307 steady encoded FPS.

The recorder's default H.264 VLC setting now reaches NVENC as CAVLC. The UI does not expose an entropy-coder control; command-line users can request CABAC explicitly. In a locked 1.0-motion source test, explicit CAVLC with a 50 Mbps VBR request saved 32,392 consecutive H.264 IDs over 90 seconds without starvation and with pool high-water 15/48. A same-build 20-second CABAC control missed 41 IDs and filled the pool. The rebuilt default CAVLC path then saved 7,200 consecutive IDs in a 20-second high-motion recording with two audio tracks and a valid replay export. These are workload-specific results; the 90-second CAVLC file measured about 83 Mbps against the 50 Mbps average target.

Output resolution defaults to native capture dimensions (`--resolution` is omitted). Settings also offers common presets and custom even dimensions from 4 to 16,384; output scaling uses the selected two-pass GPU conversion path, and hardware/profile limits may reject a requested size. Bitrate mode is the default and bitrate is editable from 1 to 500 Mbps. CQP is explicitly selectable as an experimental mode with QP 0–51 and saved default QP 28; the bitrate control is disabled while CQP is selected, and the backend sends `--qp N` without a bitrate argument. Bitrate remains saved so users can switch back without losing it. The recorder rejects an explicit bitrate combined with `--qp`. One H.264 QP 28 live color-chart capture on an RTX 3090 Ti encoded and decoded 1,080 valid, nonblack images with mean bar MAE 0.54 and maximum channel error 2; one adjacent source ID was skipped near startup. Other QPs, codecs, drivers, and device combinations remain experimental and may be rejected during encoder initialization.

The capture FPS cap defaults to `0` (uncapped compositor/display cadence) and offers 60, 120, 240, or 360 FPS. A compositor-timestamp token bucket limits frames admitted for recording to the configured rate plus at most two frames of burst credit. Capture requests are also paced for 60, 120, and 240 FPS; at 360 FPS they remain immediate to avoid missing presentations while waiting for a timer. The recorder preserves compositor timestamps, does not synthesize frames, and does not promise the chosen cap as a measured output rate. Earlier H.264 checks at 60, 120, and 240 produced 59.8, 119.1, and 237.5 captured FPS with zero black frames or internal drops under the previous request pacer; the revised 60, 120, and 240 FPS caps passed guarded ten-second NVENC checks with valid, nonblack sampled source IDs and no internal drops or pool starvation; mean steady encode rates were 59.7, 119.4, and 236.6 FPS, respectively. A separate uncapped, low-motion H.264 run verified 21,600 consecutive source IDs over 60 seconds at about 360 encoded FPS. The former request-paced 360 cap averaged 352.9 FPS and missed 64 source IDs in eight seconds. The revised timestamp-based 360 cap and a matched uncapped control each encoded 2,881 consecutive, valid, nonblack source IDs in eight seconds with zero internal drops or pool starvation while the fullscreen source remained visible.

Rate control defaults to bitrate mode at 50 Mbps. The bitrate field is labeled “Average bitrate target”; its note and tooltip explain that it is not a maximum bitrate or file-size limit and that Statistics shows the observed output bitrate. Settings persist `recording/rateControl` (`bitrate` or `constant_qp`) and `recording/qp` (default 28). Selecting CQP enables the bounded QP field and disables the bitrate field; switching back restores the saved bitrate. CQP is labeled experimental because only H.264 QP 28 has been live checked on one RTX 3090 Ti setup; a single startup source ID was skipped, while every decoded image was valid and nonblack and chart colors were within a maximum channel error of 2. The UI passes `--qp N` without an explicit bitrate argument because the recorder treats the two modes as mutually exclusive. NVENC B-frame controls are opt-in. The H.264 B-frame-2 recording and replay passed a short numbered-source check, while HEVC B-frame-2 did not sustain source cadence in its twelve-second run; default zero retains the longer validated I/P-only path.

H.264 remains the default codec. HEVC is labeled experimental and requires an explicit, persisted acknowledgement before the UI enables either standard recording or replay-only capture. The warning reports the 10-second 1440p Vulkan Video test at a 120 FPS cap: 1,192 decoded valid frames at about 119 FPS with zero black frames, plus the 60-second NVENC source-ID check at depth 4 and pool 48. A previous Vulkan Video run at a 360 Hz source encoded about 123 FPS. A separate 60-second high-motion HEVC NVENC capture passed with 21,599 consecutive source IDs. This does not establish general HEVC performance: high-motion Vulkan sessions, game capture, longer Vulkan sessions, alternate NVENC presets, and other hardware/configurations remain unvalidated. Previously saved HEVC settings without acknowledgement remain selected but Start is blocked; the UI never changes the codec silently.

## Workflow contract

| Operation | Trigger | Pending | Success | Failure/recovery |
|---|---|---|---|---|
| Manage scene profiles | Select, add, rename, edit output, or remove in Scenes & Sources | Changes persist locally; controls disable while recorder session is busy | Selected output is reflected in preview header and next recorder launch | Keep the prior profile on cancel; reject blank or duplicate names and blank output names; retain one scene |
| Start recording | Start recording | Stable button + “Starting” | Show “Recording” only after QProcess reports started; display generated MKV path | Keep inline status and engine log; correct executable/output/engine issue and retry |
| Start replay-only session | Start replay-only session while idle with history configured | Launch replay-only engine; show “Starting replay-only session” | Identify replay-only mode from process/telemetry; no primary output file is shown | Keep inline status and engine log; do not treat missing primary MKV as failure |
| Stop recording | Stop recording | Send SIGINT once; lock start/stop controls | Show “Recording saved” only after a zero exit status and engine close | If the process exits abnormally, show “Recording could not be finalized” and expose diagnostics |
| Stop replay-only session | Stop replay-only session | Send `stop` and wait for shutdown; use SIGINT only as a fallback | Show cleanly stopped; do not expect a primary output file | Keep the window open on process failure and expose diagnostics |
| Start replay | Start replay buffer | Send `start_replay`; show pending until acknowledgement | Mark active from acknowledgement/telemetry | Keep reported state and show the engine's reason |
| Stop replay | Stop replay buffer | Send `stop_replay`; show pending until acknowledgement | Mark stopped while retaining history for save | Keep reported state and show the engine's reason |
| Save replay | Save replay | Send an absolute path only while telemetry reports an enabled replay ring; show pending until engine acknowledgement | Acknowledge only after the engine confirms the saved path | Show the engine's failure reason in Controls and the engine log |
| Change audio controls | Move gain slider or toggle mute on a streaming source | Send a typed audio control line; keep the reported control value until acknowledgement | Apply the acknowledged value and state in the row | Restore the last reported value and show the error or acknowledgement timeout |
| Change settings | Open Settings, edit, Save changes | No autosave | Persist local configuration and update controls | Preserve values and show inline validation; cancel explicitly discards edits |
| Close during capture | Close window while recording or replay-only capture is active | App-owned confirmation names the active mode | Send the mode-appropriate stop request, wait for process exit, then close | Keep the window open if stop fails or times out |

Starting and stopping a recording require no confirmation. No duplicate process or stop signal is dispatched while that operation is pending. Engine output is diagnostic content, not a success claim.

## Navigation and responsive behavior

- One `QMainWindow`; docks are user-resizable and their layout is restored locally.
- View menu can restore closed panels. Preview is the central widget and cannot be hidden. Scenes & Sources selects a saved single-output profile for the next capture session.
- Lower workspace tabs are peer views (Audio mixer, Statistics), use native keyboard behavior, and maintain their own contents.
- At narrow window widths, dock panels can be hidden/floated; core controls remain reachable in the Controls dock and menu.
- Long engine paths wrap or elide visually, with the full value available in a tooltip/accessibility description.
- Do not steal focus when telemetry refreshes. Restore focus to the initiating action after Settings closes.

## Overlays and feedback

- **Dialog primitive:** Native Qt `QDialog` with explicit title, description, and labeled controls.
- **Confirmation:** App-owned dialog before closing an active recording; default to keeping the window open.
- **Status:** Persistent status and error labels beside recording controls; errors stay visible until a new operation replaces them.
- **Engine log:** Optional read-only dock, capped to a bounded number of lines.
- **Disabled actions:** Explain the missing engine feature in text/tooltips; color is never the only signal.
- **Settings cancel:** Explicit “Discard changes”; closing a dirty Settings window asks before discard.

## Async and resilience

- QProcess and UI event dispatch are asynchronous. Process I/O is handled by Qt; no waiting/blocking calls occur on the widget thread.
- Stop sends SIGINT and allows up to eight seconds to flush before a forced termination is considered a failure. The UI never reports the file as saved before a clean process exit.
- Telemetry is bounded to complete JSONL lines. Malformed or unknown lines are ignored and logged without replacing the last valid readings.
- If telemetry pauses, keep the last values visible and mark them stale after three seconds. A process error remains visible until the next recording attempt.
- Closing during recording cannot silently abandon the child. Wait for graceful finalization before accepting close.
- Settings are local `QSettings`; no recording is queued offline and no engine retry starts automatically.

## Validation and accessibility

- Scene names are non-empty and unique without regard to case; every profile keeps one non-empty Wayland output name. Picker availability reflects Qt's current Wayland screen list; the recorder checks the selected name at startup. A manually entered or stale name is not claimed as confirmed. A blank or missing engine path remains visibly unavailable. Backend, codec, rate-control mode, NVENC preset, NVENC B-frame, and GPU frame identity diagnostic controls have accessible names. The NVENC preset and B-frame controls are hidden and disabled for Vulkan Video; the async-depth label and guidance identify the selected backend, and its separate saved value is restored when switching back. Bitrate, QP, GOP/keyframe interval, frame-pool size, each backend's async depth, NVENC B-frame count, and replay duration use bounded numeric controls with explicit ranges or units.
- Focus all controls by keyboard; show a high-contrast focus outline. Every icon-only control has an accessible name and tooltip.
- Status text accompanies colored dots; all measurements include units and an accessible “Not reported” state.
- Do not expose a fake preview surface or CPU copy. The current preview uses a downscaled GPU-produced DMA-BUF surface with ownership separate from the recording path.
- Verification for this shell: CMake build, `--smoke` offscreen startup, actual event-loop exit, theme-token drift check, and design token lint/audit where the tool supports a native Qt project.
