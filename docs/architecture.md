# Engine architecture and evidence log

## Target and current status

The target is the live DP-1 Dell AW2725DF at 2560×1440 and 359.979 Hz, on the RTX 3090 Ti with NVIDIA driver 615.71.09. A four-second H.264 color-chart recording through a source-built FFmpeg 9.0.2 BGRA-to-B8 mapping produced 1,441/1,441 consecutive IDs, no black or malformed frames, and mean bar RGB error of 0.78 code values. A 60-second low-motion CAVLC run captured, submitted, encoded, and muxed 21,600 frames at a mean steady 360.1 FPS. The pool peaked at 24/48 with zero starvation or internal drops; independent offline decoding verified every ID from 212 through 21,811 in order, with no black, invalid, duplicate, backward, or missing IDs. That Vulkan Video run establishes a clean 60-second result for its low-motion workload. Production NVENC passed separate 60-second low-motion H.264 and HEVC source-ID runs with 21,598 and 21,596 consecutive decoded IDs. A locked high-motion source passed 60 seconds on HEVC NVENC and **90 seconds on H.264 NVENC with explicit CAVLC and a 50 Mbps VBR request**, the latter decoding 32,392 consecutive IDs with pool high-water 15/48. A fresh ten-second H.264 default run omitted backend, preset, coder, and async-depth options and decoded 3,601 consecutive high-motion source IDs. The rebuilt default CAVLC path also passed a 20-second high-motion recording with audio and replay export. Game workloads and indefinite high-motion headroom remain unproven.

The offline source-ID decoder defaults to luma threshold 100. This calibration recovered 21,654 consecutive IDs in a 60-second high-motion replay export, 32,392 in the 90-second H.264 CAVLC run, and 21,599 in the high-motion HEVC run; it also preserved black classification for 54 frames in the depth-eight H.264 regression clip. The threshold override remains useful for other compressed paths.

CMake now requires source-patched private `libavutil`, `libavfilter`, and `libswscale`, validates their versions and Vulkan behavior, and embeds their directory in the recorder's `DT_RPATH`. The B8 format mapping corrects the captured colors. The conditional Vulkan filter wait is enabled for HEVC and for the selected NVENC backend; the latter uses default async depth four because depth eight still produces periodic black frames. The direct native-size converter remains experimental after producing a black frame every ninth output in its tested configuration. An opt-in private FFmpeg callback feeds completed Vulkan conversion timestamps into recorder telemetry. NVENC hardware submission/completion timestamps remain unavailable. The separately built opt-in NVENC diagnostic reports API wall spans and a PTS-matched host interval from accepted submission return to successful bitstream-lock return. That interval includes queueing, host scheduling, and driver wait; it is an availability proxy, not hardware execution time. The [measurements](measurements.md#2026-09-28-isolated-nvenc-host-api-timing) describe earlier API-span runs; the new proxy has not yet been live-tested.

The capture contract is GPU-resident rather than literally free of all GPU copies. `ext-image-copy-capture-v1` copies a compositor frame into a client-supplied DMA-BUF; a copy on the GPU is permitted. The forbidden operation is CPU access to raw video pixels.

## Capture ownership

1. Bind the DP-1 `wl_output`, output image capture source manager, image copy capture manager, and Linux DMA-BUF manager.
2. Create an output capture session and collect its `buffer_size`, `dmabuf_format`, and `dmabuf_device` constraints through `done`. These session constraints, rather than general display feedback alone, select the destination format and modifier.
3. Allocate a pool of GPU memory with matching dimensions and a supported format/modifier. Export DMA-BUF plane FDs, strides, and offsets; create one `wl_buffer` for each slot. Neither allocation nor capture may map pixel memory on the CPU.
4. Create one capture frame object, attach a free buffer, request the capture, and dispatch Wayland events. On `ready`, record source presentation time and transfer a lease for that slot to the GPU stage. Destroy the frame object before requesting another capture. `wl_buffer.release` is not a signal for this protocol.
5. A slot remains leased until the GPU reader has completed. If all slots are busy, count starvation periods and elapsed time; the protocol does not reveal how many source presentations were missed during that interval. Never let the compositor overwrite a slot still read by a GPU queue.

The protocol permits only one outstanding frame object per session. A deeper destination pool overlaps later GPU work with the next compositor copy, but cannot make capture requests concurrently. After a ready frame, the compositor may wait for content to change before satisfying the next request. Both properties may limit real capture rate, so request-to-ready latency and distinct presentation timestamps are required measurements.

The capture module checks known-format plane counts, strides, offsets, and arithmetic extents before passing buffers to linux-dmabuf. It cannot prove an FD's allocation size from the current plane descriptor alone; the GPU allocator must supply valid DMA-BUFs. The compositor can treat a too-short buffer as a fatal protocol error. Pool exhaustion is reported separately as starvation duration, since the protocol does not expose a count of compositor frames missed while no slot is free.

## GPU and encode decision

The installed NVIDIA Vulkan device exposes DMA-BUF external memory, DRM modifiers, and H.264/HEVC Vulkan Video encode extensions. The explicit Vulkan Video backend imports live AR24 compositor DMA-BUF frames with `av_hwframe_map(..., AV_HWFRAME_MAP_READ | AV_HWFRAME_MAP_DIRECT)`, feeds Vulkan-only conversion filters, encodes with FFmpeg's `h264_vulkan` or `hevc_vulkan`, and writes MKV through a separate worker. The runtime output is checked for `AV_PIX_FMT_VULKAN` and NV12 storage before encode; FFmpeg graph auto-conversion is disabled. A five-second H.264 run encoded and muxed all 1,734 captured frames, but its uncontrolled desktop average was 346.8 frames/s.

The tested two-pass path is DMA-BUF → Vulkan import → two FFmpeg Vulkan filter passes for NV12 conversion/scaling → Vulkan Video H.264/HEVC hardware encode. The live path imports the exact negotiated NVIDIA block-linear modifier and holds each capture lease until the corresponding compressed packet returns. NVIDIA encoder-engine utilization was observed during live recording. The unpatched host FFmpeg build maps BGRA frames to `VK_FORMAT_R8G8B8A8_UNORM`, which swaps red and blue for these little-endian AR24 capture bytes. The private `libavutil` patch selects `VK_FORMAT_B8G8R8A8_UNORM`; the private `libavfilter` patch conditionally waits for a completed Vulkan filter submission when HEVC or H.264 ULL needs it. The repo build helper installs the libraries under ignored `.deps/`, and CMake embeds that directory in the recorder's `DT_RPATH`. The source-built B8 library produced the color-correct chart and 60-second recording described above. A custom native-size compute converter is a separate experimental option; its failure history is below.

The headless CLI defaults to FFmpeg's `h264_nvenc` or `hevc_nvenc` API wrapper; use `--backend vulkan` to select `h264_vulkan` or `hevc_vulkan` through Vulkan Video. With no CLI backend argument, `FLUXREC_GPU_ENCODER_BACKEND` remains a diagnostic override. The NVENC route transfers Vulkan NV12 planes into a separate CUDA pool with a GPU-to-GPU copy before encode; it is not allocation-level zero-copy. Source inspection and a short syscall trace found no CPU mapping, read, or copy calls on the traced DMA-BUF descriptors, but those checks cannot rule out every user-space load or driver-internal stage. H.264 defaults to CAVLC, whose high-motion 50 Mbps-request run passed 90 seconds on the tested RTX 3090 Ti. HEVC passed the documented 60-second high-motion check but has less workload coverage. A production input-audit proxy on the loaded system codec observed one successful initialization, four `CUDADEVICEPTR` registrations, and zero non-CUDA registrations or software input-buffer create/lock calls. This confirms the NVENC input branch for those sessions, not the preceding Vulkan/CUDA transfer or driver-internal behavior. Vulkan Video uses `max_b_frames=0` and requests low delay. NVENC defaults to the same zero-B-frame policy and exposes an opt-in count of 0–4 through the CLI and UI; nonzero counts use encoder packet PTS/DTS and add frame reordering. The output-resolution control is a Vulkan scaling request subject to codec and device limits, and the FPS control caps capture requests while preserving compositor presentation timestamps. Hardware quality-level and Vulkan Video B-frame capability queries are not yet exposed as user controls.

The direct native-size conversion shader is at `gpu/shaders/convert_xrgb_to_nv12.comp`. In the unpatched host FFmpeg import, little-endian AR24 is represented by an R8 view, so sampled red and blue components are reversed. The shader writes R8 and R8G8 temporary images; Vulkan copy commands write their planes into one multi-planar NV12 image accepted by Vulkan Video. In the tested configuration, every ninth decoded frame was black with encoder async depth eight. A same-dispatch diagnostic sampled all-zero RGB texels on those frames before conversion, while the affected capture pool slot varied. An opt-in external-queue acquire/release experiment left the same every-ninth fault. The cause remains unresolved, and this path is experimental until decoded image checks pass. For the two-pass path, native-size RGB-to-NV12 conversion failed during FFmpeg graph setup, so the first `scale_vulkan` pass converts at width and height minus two pixels and the second restores native dimensions. That extra scaling adds GPU work and may introduce scaling artifacts.

Direct desktop DMA-BUF → CUDA external-memory import is not a safe design assumption: NVIDIA's CUDA Driver API 13.4 documents `CU_EXTERNAL_MEMORY_HANDLE_TYPE_DMABUF_FD` import as supported only on Tegra starting with Thor. The Vulkan modifier import path must query the exact format, modifier, and usage combination rather than interpreting NVIDIA's opaque block-linear layout on the CPU.

## Concurrency model

```text
Wayland event thread → leased DMA-BUF queue → GPU conversion/encode submissions
                                                ↓
                                     compressed packet queue
                                        ↙              ↘
                              Matroska writer      replay ring
```

Every queue has a fixed capacity and reports current occupancy, high-water mark, and drops. Wayland dispatch, GPU submission, encode completion, packet muxing, replay snapshots, disk writes, audio, and UI use separate workers or nonblocking callbacks. The UI subscribes to copied telemetry snapshots and never owns the capture worker.

`PacketRouter` ingress is single-producer/single-consumer: callers must submit from one producer thread. Its packet telemetry counts the 512-entry waiting ring and excludes the worker's current packet. The ring caps queued payload at 64 MiB; the worker can hold one additional packet up to 64 MiB, so the ingress ring plus its current packet can account for up to about 128 MiB of payload. Downstream queues may retain packets after fanout.

The recorder's packet router receives CPU-visible *compressed* H.264/HEVC bytes, appends shared packet references to a bounded replay ring when configured, and forwards them to a separate Matroska writer worker. A separate audio forwarding worker can share compressed AAC/Opus packet references with both the live mux and replay ring. A stdin control service snapshots the ring and exports selected video and audio packets on its own worker, merging them by absolute DTS before they enter the bounded mux queue. `MuxWriter` adjusts the shared audio origin by the first selected video packet's DTS before rebasing video, so live recordings and replay exports preserve presentation alignment when the encoder reorders frames. Replay exports begin audio at or after the selected video keyframe; the exporter keeps the original capture origin and leaves this single timestamp adjustment to `MuxWriter`. The exporter integration fixture checks strict per-stream DTS, global packet order, and A/V sync at both window endpoints with reordered video. A 70-second replay-only session exported a 60-second high-motion history with 21,654 consecutive H.264 IDs and two AAC tracks. A 140-second session then saved a 120-second history at 130 seconds, producing 43,252 consecutive H.264 IDs and two AAC tracks with strict DTS and zero drops, replay rejects, or pool starvation.

With `--audio on`, two PipeWire streams capture the desktop monitor and microphone. Audio encoding and replay forwarding run outside the capture callbacks, and a bounded audio-packet bridge forwards compressed packets without waiting on disk. The first compositor presentation timestamp sets a shared monotonic origin for video and audio. Before the first video packet establishes its DTS, `MuxWriter` holds queued audio and reserves one bounded packet slot for that video; the queue may briefly contain that one extra video packet and up to one extra packet's payload, with total bytes capped at twice the configured limit. Shutdown without any video packet drains audio with a zero DTS adjustment. Once known, the first video DTS offset is added to the audio origin before audio timestamps are written. With zero B-frames, the offset remains zero. The recorder waits for both audio codec formats before creating the Matroska header. In replay-only mode, audio can be enabled with `--audio on`; it is stored in the bounded replay ring without creating the primary mux. Audio is off by default while the required sources are not guaranteed to exist on every host.

When an AAC input frame contains fewer than `frame_size` sample frames, the encoder pads its tail with silence. The audio worker stores the per-channel padding count in a fixed eight-entry PTS tracker until the delayed AAC packet with the same input-frame PTS arrives. The compressed packet carries that count through live muxing and replay snapshots/exports. `MuxWriter` converts it to `AV_PKT_DATA_SKIP_SAMPLES` discard-padding metadata; Matroska writes this as `DiscardPadding`. AAC encoder `initial_padding` remains separate and continues to populate Matroska `CodecDelay`, so leading priming removal and trailing partial-frame removal are preserved independently. Full frames carry no added metadata.

Ext image copy capture has no per-frame fence FD in its API. Its `ready` event is the producer completion signal for the destination. GPU consumer completion must be tracked separately before a slot is returned to the pool. Frame ownership and queue synchronization must be verified under sustained load; CPU waits in the capture event thread are forbidden.

## GPU preview path and live check

The preview uses an optional Unix `SOCK_SEQPACKET` channel. The recorder downsamples encoder-input NV12 frames to a 960×540 RGBA DMA-BUF with Vulkan, capped at 60 preview frames per second, and sends the buffer FD with an acquire fence. The Qt Quick consumer imports and renders it through Vulkan, then returns a release fence. This path does not map or copy raw pixels through CPU memory, and preview work uses a separate queue from capture and encode.

A live UI smoke with the source-built B8 library brought the QML item up and displayed frames: `has_frame` was true in 515 mid-run samples, with 324 visible frame swaps. The producer published 175 preview frames with no preview drops or full-pool skips; the consumer reported 174 releases before shutdown, leaving one publication outstanding at process exit. Concurrent recording captured, submitted, encoded, and muxed 300 frames with zero drops or capture-pool starvation. `ffprobe` found 300 H.264 packets at 2560×1440 and offline `framemd5` decoded all 300. A separate five-second test stopped the UI process while its child recorder continued writing, then decoded 3,453 consecutive source IDs. This establishes recorder independence through that pause; longer preview-release handling remains to be tested.

## Measurement requirements

For each workload and requested rate (60, 120, 240, 360 FPS), collect: compositor capture completions, distinct source presentation timestamps or stronger GPU content identity, GPU submissions, encoded packets/frames, muxed frames, every drop reason, duplicated frames, stage latency distributions, pool/queue occupancy, encoder utilization, and output bytes. A 360 FPS container timebase alone is insufficient. Idle desktop rates cannot establish unique 360 FPS content if Hyprland has nothing new to present.

The no-CPU-pixel claim requires source inspection for mapping/download/copy paths plus runtime tracing of DMA-BUF mappings and FFmpeg hardware-frame operations. Compressed packet access by CPU is expected and permitted. The [NVENC raw-pixel residency audit](nvenc-zero-cpu-pixels.md) combines source checks, a three-second DMA-BUF syscall trace, and production input-proxy observations at the loaded NVENC boundary. The proxy confirms CUDA-device-pointer registration and no software input-buffer branch in the tested sessions. Earlier Vulkan/CUDA stages, ordinary CPU loads through existing mappings, and driver-internal staging remain outside that proxy's coverage.
