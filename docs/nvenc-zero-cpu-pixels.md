# NVENC raw-pixel residency audit

## Conclusion and scope

Source inspection and a successful opt-in runtime route audit support that Fluxrec's normal two-pass NVENC route does not map, download, or process raw video pixels on the CPU. In the audited session, FFmpeg reported a successful DMA-BUF-to-Vulkan import, both Vulkan compute stages, and a Vulkan array-to-CUDA device-memory copy; the NVENC proxy observed CUDA device-pointer inputs. The CPU handles descriptors, timestamps, control data, telemetry, and compressed packets.

This is GPU-resident processing, not allocation-level zero-copy. The compositor copies into Fluxrec's capture DMA-BUF; two Vulkan filter passes convert and scale BGRA/BGR0 to NV12; FFmpeg copies the Vulkan NV12 planes into a separate CUDA NV12 pool. Route identity markers are first-success samples per frame context or filter instance. A later strict run also emitted aggregate successful-operation counts for each route stage; those counts matched recorder submissions but do not correlate exact PTS sets. The importer marker's `cpu_mapping=none_in_importer` describes the inspected FFmpeg source path; it cannot rule out proprietary driver-internal staging or other CPU access outside that importer.

The application loads private FFmpeg 9.0.2 `libavutil`, `libavfilter`, and `libswscale` from `.deps/ffmpeg-bgra-b8/lib`; the manifest records `CONFIG_CUDA` and Vulkan-to-CUDA transfer support. `ldd build-root/engine/fluxrec-record` resolves `libavcodec.so.63` from `/usr/lib`, not from that private directory. The FFmpeg 9.0.2 `nvenc.c` reference below describes the source snapshot inspected, while the live NVENC API audit below observes the exact loaded codec's calls at the driver boundary. `patches/README.md` explains that the helper compiles the Vulkan Video object but does not build or stage a private `libavcodec`.

## Frame path and fail-closed checks

1. **DMA-BUF to Vulkan.** `GpuEncoder::Impl::initialize` in `gpu/gpu.cpp:625-663, 746-803` requires the Vulkan device to match the capture render node, sets `AV_PIX_FMT_VULKAN` with BGRA or BGR0 storage for imported frames, and probes the direct import before capture starts. `GpuEncoder::Impl::submit` at `gpu/gpu.cpp:1736-1770` repeats `av_hwframe_map` for each capture with `AV_HWFRAME_MAP_READ | AV_HWFRAME_MAP_DIRECT`. FFmpeg defines DIRECT as requiring no copies during map/unmap (`.deps/src/ffmpeg-9.0.2/libavutil/hwcontext.h:526-531`); `av_hwframe_map` dispatches to the hardware map callback without inserting a transfer fallback (`hwcontext.c:793-850`). The private Vulkan implementation, `vulkan_map_to`, `vulkan_map_from_drm`, and `vulkan_map_from_drm_frame_desc` (`hwcontext_vulkan.c:3257-3537, 3664-3690, 4069-4092`), creates a DRM-modifier Vulkan image and imports/binds the DMA-BUF FD as external memory. Import errors abort the operation.

2. **Vulkan conversion and scaling.** `GpuEncoder::Impl::initialize_filter_and_encoder` (`gpu/gpu.cpp:1253-1427`) disables filter-graph auto-conversion, creates a `scale_vulkan` BGRA/BGR0-to-NV12 pass at capture width/height minus two, then an NV12-to-NV12 pass at output dimensions, and requires a Vulkan/NV12 sink. FFmpeg's `scale_vulkan_config_output` allocates its CPU `SwsContext` only when formats differ and at least one dimension is unchanged (`.deps/src/ffmpeg-9.0.2-filterwait/libavfilter/vf_scale_vulkan.c:326-383`); `scale_vulkan_filter_frame` otherwise runs `ff_vk_filter_process_simple`, using `sws_scale_frame` only when that context exists (`:260-314`). The configured first pass changes both dimensions; the second keeps NV12, so the CPU branch guard is false for both.

3. **Vulkan to CUDA.** `GpuEncoder::Impl::encode_filtered_frame` (`gpu/gpu.cpp:1512-1611`) rejects non-Vulkan or non-NV12 filter output, allocates from the CUDA hardware-frame pool, calls `av_hwframe_transfer_data`, and returns an error if transfer fails. FFmpeg's generic `av_hwframe_transfer_data` chooses the Vulkan source callback for hardware-to-hardware frames (`.deps/src/ffmpeg-9.0.2/libavutil/hwcontext.c:448-485`). In the private `vulkan_transfer_data_from`, the CUDA path is enabled only when external FD memory and semaphore extensions are present (`hwcontext_vulkan.c:4957-4980`). `vulkan_transfer_data_to_cuda` imports the Vulkan image memory and semaphores, waits on the external semaphore, issues `cuMemcpy2DAsync` from `CU_MEMORYTYPE_ARRAY` to `CU_MEMORYTYPE_DEVICE`, and signals completion (`hwcontext_vulkan.c:3760-4000, 4863-4954`). The destination CUDA pool uses `cuMemAlloc` (`hwcontext_cuda.c:114-136`). If Vulkan interop extensions are unavailable, the Vulkan callback returns `ENOSYS`; the CUDA callback then rejects a non-CUDA hardware source (`hwcontext_cuda.c:240-254`). Interop errors also propagate, and Fluxrec surfaces either failure. It does not convert those failures into a software-frame path. Production code also checks the transfer result is `AV_PIX_FMT_CUDA` with a CUDA hardware-frame context and NV12 storage (`gpu/gpu.cpp:1683-1696`); a mismatch frees the frame and fails encoding.

4. **CUDA frame to NVENC.** `GpuEncoder::Impl::open_nvenc_encoder` sets `AV_PIX_FMT_CUDA` and the CUDA frame context, then checks that the opened encoder retained that format (`gpu/gpu.cpp:848-1000`). In the FFmpeg 9.0.2 source snapshot, `nvenc_register_frame` registers a CUDA frame as `NV_ENC_INPUT_RESOURCE_TYPE_CUDADEVICEPTR`, and `nvenc_upload_frame` takes the direct hardware-resource branch for CUDA (`.deps/src/ffmpeg-9.0.2-filterwait/libavcodec/nvenc.c:2223-2275, 2277-2336`). Its alternate branch locks an NVENC input buffer and calls `nvenc_copy_frame`; that branch is guarded by an input format other than CUDA/D3D11. The live driver-boundary check below observed which branch the loaded system codec actually used.

The general Vulkan hardware-frame API can download into software frames through `vulkan_transfer_frame`, and the CUDA transfer helper can copy to/from host memory when one side is software. Those branches do not apply to this call: Fluxrec supplies a populated CUDA hardware frame and a Vulkan hardware frame. If Vulkan-to-CUDA external interop cannot run, both hardware-frame callbacks reject the transfer and Fluxrec fails the frame.

## Runtime evidence boundary

The earlier `strace` mapping run in `docs/measurements.md` covers Vulkan Video only. A separate three-second production NVENC trace now covers the H.264 two-pass route with the default CAVLC coder. `strace -f -yy` followed `mmap`, file-read/copy calls, `fcntl`, `dup*`, and `close*`; `FLUXREC_GPU_DMABUF_SYNC_PROBE=1` logged 219 observational samples spanning 43 capture slots. The trace annotated capture and duplicate FDs as `</dmabuf:>` and recorded 1,086 `fcntl`, 1,980 `dup`, and 3,106 `close` calls involving those FDs, but **zero `mmap` or traced file-read/copy calls on any DMA-BUF-annotated FD**. The recorder captured and muxed 989 frames. Tracing introduced 32 brief pool-starvation periods, so this run is a pixel-access check, not a throughput result. Artifacts: `.validation/nvenc-pixel-audit-20260928.{strace,stderr.log,stdout.log,mkv}`.

That syscall evidence covers the observed three-second process and FD-based access methods. It cannot detect ordinary CPU loads through an existing mapping, user-space `memcpy`, Vulkan/CUDA API-level operations, or driver-internal staging. The probe sampled 43 of the 48 configured capture slots, while `-yy` annotated DMA-BUF descriptors throughout the syscall trace. The source-path checks above remain necessary to support the no-CPU-pixel-processing claim. `dmabuf_import_cpu` and `cuda_transfer_cpu` telemetry values are host call durations, not pixel-access traces. Vulkan timestamp queries cover the two scale dispatches; they do not inspect NVENC input handling.

An opt-in NVENC function-table proxy now observes the **loaded system codec** at `nvEncInitializeEncoder`, `nvEncRegisterResource`, `nvEncCreateInputBuffer`, and `nvEncLockInputBuffer`; the calls are forwarded to the real NVIDIA library. The proxy pins NVENC API 13.1 structure layout and rejects mismatched outer versions. In a controlled four-second production H.264 NVENC CAVLC recording, it reported one successful encoder initialization, **four CUDADEVICEPTR registrations, zero other resource registrations, and zero software input-buffer create or lock calls**. The same session saved **1,441 consecutive, valid, nonblack source IDs** with no capture drops or pool starvation. The normal, optional VBR-max-rate, and explicit CBR reports all passed the proxy's input-path checks. Artifacts: `.validation/nvenc-input-audit/production-cavlc-4s-13_1-rczero.{json,mkv*}` and adjacent `production-vbr50-max60-4s.*` and `production-cbr50-4s.*`; the diagnostic and fail-closed self-tests are described in [`tools/nvenc_input_audit/README.md`](../tools/nvenc_input_audit/README.md).

This proves that these sessions supplied CUDA device-pointer resources to NVENC without taking its software input-buffer branch. A registration is per CUDA surface, not per encoded frame; the zero software-call counts cover the observed sessions. The proxy does not inspect pixel values, ordinary CPU loads through pre-existing mappings, or proprietary driver internals. The private FFmpeg route markers and DMA-BUF syscall trace support those separate path claims; the route probe is described in [`docs/ffmpeg-zero-cpu-route-audit.md`](ffmpeg-zero-cpu-route-audit.md). A syscall-only trace cannot establish the Vulkan and CUDA API-level details recorded by that probe.

In the stricter 2026-09-28 route run, FFmpeg's process summary counted 3,601 live DMA-BUF imports, 3,601 successful dispatches in each Vulkan scale stage, and 3,601 successful Vulkan-to-CUDA submissions. The NVENC proxy counted 3,601 successful picture submissions backed by mapped CUDA device pointers; software input-buffer create/lock calls were zero. These counts matched the recorder's 3,601 submitted and encoded frames for the same PID and run ID. They establish aggregate successful API submissions for that session. Equal totals do not prove that all stages processed the identical PTS set, that GPU work completed for each frame, or what the closed driver did internally. Offline decode independently found 3,601 consecutive nonblack IDs, 296–3,896. See the strict-run record and the earlier teardown-accounting verifier failure in [`docs/ffmpeg-zero-cpu-route-audit.md`](ffmpeg-zero-cpu-route-audit.md).
