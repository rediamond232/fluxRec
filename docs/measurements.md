# Measurement log

These measurements include source-ID-verified 2560×1440 H.264 and HEVC runs near 360 FPS on both low- and high-motion workloads, plus recording with audio and replay export. A 20-second direct capture of the authenticated Minecraft practice world while it was simulating (debug counter 2,374 and 2,847 FPS) followed the 359.979 Hz display; that arena was not GPU-bound. Earlier Minecraft files include a server pause and are not the same result. CS2 and sustained throughput in a GPU-saturated game remain unvalidated. Independent physical audio-clock drift and indefinite throughput remain open. Commands and conditions are recorded so later runs can be compared without treating a container timebase as capture throughput.

Host: RTX 3090 Ti, NVIDIA driver 615.71.09, Hyprland 0.56.2, DP-1 Dell AW2725DF at 2560×1440 and 359.979 Hz. The desktop was in ordinary use; the motion workload was uncontrolled. ## Encoder-only API probe

FFmpeg 9.0.2 on this host successfully encoded Vulkan NV12 frames to H.264 MKV through `h264_vulkan`. In a paced longer diagnostic, `nvidia-smi` reported about 15% encoder utilization during the Vulkan Video encode. This shows the NVIDIA hardware encode engine is used; it does not establish DMA-BUF import, source pixel residency, the native-size RGB-to-NV12 conversion path, or 360 FPS recording.

The installed FFmpeg build rejected same-size Vulkan BGRA-to-NV12 conversion through `scale_vulkan` with an `Operation not supported` graph setup error. A two-pass Vulkan graph that changes both dimensions for the conversion and then resizes NV12 back to target size did encode in a diagnostic. A direct native-size GPU conversion stage remains the target.

## Exact-modifier DRM PRIME → Vulkan import probe

An isolated probe allocated a 2560×1440 AR24 GBM BO on `/dev/dri/renderD128` with the capture session's modifier `0x0300000000606010`. The NVIDIA GBM backend returned one plane, stride 10,240, offset 0, and allocation size 14,745,600 bytes. FFmpeg selected the RTX 3090 Ti Vulkan device. `av_hwframe_map` from `AV_PIX_FMT_DRM_PRIME` to `AV_PIX_FMT_VULKAN` succeeded with `AV_HWFRAME_MAP_READ | AV_HWFRAME_MAP_DIRECT`; the resulting `AVVkFrame` had a non-null image, DRM-format-modifier tiling, and `GENERAL` layout. The probe did not call a CPU pixel-map or transfer API.

The imported frame reports BGRA software format and the actual imported Vulkan image format is `VK_FORMAT_R8G8B8A8_UNORM` (enum value 37). FFmpeg's DRM import path maps AR24 to a B8 format initially, then selects the hardware-frame context's R8 format for this single-plane image. With little-endian AR24 bytes, an identity sampled view would present red and blue swapped. The native-size shader contract now requires a B/G/R/A component mapping on that R8 view (or identity mapping on a true B8 view). This color path still needs an encoded visual test. The import proof does not yet include a live compositor-captured frame flowing into the encoder.

## Full recorder host-mapping trace

A separate three-second H.264 recorder run under `strace -f -qq -yy -e trace=mmap,mmap2,munmap` completed with 991 encoded/muxed packets and a 2.989-second MKV. The trace contained 1,306 mapping-related syscall lines. No `mmap` line named a `/dev/dri` device or DMA-BUF FD, and no mapping had the 14,745,600-byte captured-frame allocation size. It did contain 17 mappings on `/dev/nvidia0` and 252 on `/dev/nvidiactl`, mostly driver control/queue allocations; therefore a blanket claim of no GPU-device mappings would be false. Source inspection found no `hwdownload`, `av_hwframe_transfer_data`, `sws_scale`, raw-pixel `memcpy`, or CPU image-map call in the recorder path. The only per-frame host copy found is of compressed encoded packet bytes. These observations support the no-CPU-raw-pixel design but do not independently inspect the closed NVIDIA driver's internal behavior. `nvidia-smi dmon` sampled encoder utilization of 65–73% during the run.

Tracing reduced throughput and caused 86 pool-starvation periods totaling 162.165 ms, so this run is evidence about memory access and hardware encoder use, not a performance benchmark. It also showed four completed capture frames left in the queue at shutdown, matching the shutdown-drain issue documented above.

The larger pool appears to better absorb encode latency, while the shutdown drain must be fixed before its true encoded count can be reported.

The verifier decodes saved video offline and is not in the recording path.

## Native-size compute conversion first smoke (optimization in progress)

The first direct-only converter attempted to give `h264_vulkan` separate R8 and R8G8 images as its NV12 input. The encoder requires one multi-planar NV12 image and rejected that representation after four captures; no usable encoded frames resulted. The corrected direct path writes R8/R8G8 temporary images with the custom compute shader and copies both planes on the GPU into a single multi-planar Vulkan Video input image. A three-second live smoke then produced `/tmp/fluxrec-direct-compute-multiplane.mkv`: 46 decodable H.264 High frames, 2560×1440, TV-range BT.709, 2.910-second duration, and strictly increasing DTS in the Matroska file. This proves a native-size GPU-only conversion-to-encoder bridge on the target hardware. It is not a throughput result: per-frame temporary image allocation made the first version about 16 frames/s. Resource pooling and synchronization tuning are under way before the controlled 360 Hz benchmark.

### Controlled direct-path validation: periodic black frames

After temporary image pooling, a controlled ten-second direct-conversion run reported 3,599 captured, submitted, encoded, and muxed frames with zero internal drops or pool starvation. That count **does not establish 360 usable FPS**. The saved video has a fully black frame at decoded indices 8, 17, 26, and so on. The offline stimulus-ID verifier found 400 invalid black frames; these frames were counted by the encoder and mux telemetry. A second controlled ten-second run after correcting compute-to-transfer barrier stages still produced every-ninth black frames (3,546 decoded frames). A separate four-second run after changing non-disjoint multi-planar layout barriers to `COLOR_BIT` again showed the same pattern.

An isolated four-second run disabled all reuse of the converter's temporary images, descriptors, and command buffers. It encoded 1,440 frames but still produced 158 corrupted frames (3,160 invalid digit masks). Thus temporary resource reuse alone does not explain the fault. A second four-second run with encoder async depth one decoded 790 frames with zero invalid masks, but it had 737 capture-pool starvation periods totaling 2.236 seconds. The source stimulus presented 5,388 consecutive frames with no ID gaps during these captures. The failure therefore depends on overlap or resource reuse associated with encoder pipeline depth; GPU output checks and further depth tests are under way. Until decoded output passes the ID verifier at the target rate, the direct path is an experimental benchmark and the first milestone remains open.

A diagnostic-only Vulkan readback sampled the GPU-generated NV12 before `avcodec_send_frame` in another four-second async-depth-eight run. It observed uniform black NV12 (`Y=16`, `UV=128`) on the first failing output frames, while neighboring frames had varied luma. Waiting on the conversion timeline semaphore on the CPU before handing the image to FFmpeg did not remove the 157 invalid decoded frames. Thus the black data exists before the video encoder; the remaining investigation compares the imported RGB image, shader temporary planes, and final NV12 copy. This raw-pixel readback is enabled only by an explicit diagnostic environment variable and is not part of normal recording.

A subsequent six-second diagnostic copied both the shader's R8/R8G8 temporary planes and the final NV12 planes to diagnostic staging buffers. Their hashes and value ranges matched exactly on sampled frames. Both temporary planes were already uniform black at the first two failing PTS values (22,170 and 47,079 µs); adjacent sampled frames were nonblack. The file had 2,152 decoded frames and 4,780 invalid digit masks (239 black frames). This rules out the plane-copy step as the immediate cause and focuses the investigation on the imported RGB source or shader sampling/synchronization. The diagnostic capture had 602 pool-starvation periods because its full-frame readbacks add overhead; it is not a throughput benchmark.

An opt-in GPU frame-identity pass computes a 128-bit digest of the imported RGB image and reads back only those 16 digest bytes. In a four-second direct run with this pass enabled, all 1,440 decoded frames had valid, consecutive stimulus IDs and all 1,440 captured RGB digests were distinct. A paired direct run without the identity pass, under the same stimulus, again produced black temporary planes at the ninth and eighteenth frames and periodic black decoded frames. A standalone no-op semaphore submit, a separate source-image barrier submit, and changing the converter's input semaphore wait stage to `ALL_COMMANDS` each failed to remove the fault. The extra RGB-reading GPU workload changes the outcome, but the mechanism is not yet established; the identity pass is not being treated as a proven synchronization fix.

A later same-dispatch source probe recorded 3,600 tagged texel samples from the imported RGB view on selected frames while direct H.264 encoded 1,082 frames in three seconds. All sampled texels were zero on each of the 120 every-ninth black frames, while adjacent frames sampled nonzero content. The failing phase moved across capture pool slots. An isolated opt-in `VK_QUEUE_FAMILY_EXTERNAL` acquire before shader sampling and release afterwards then encoded 1,081 frames in about three seconds; it still produced 120 black frames, with all 3,600 tagged source texels zero on each failing frame. The injected barrier did not repair the direct-path fault. FFmpeg uses concurrent image sharing with an ignored queue-family index on this host, but Vulkan synchronization2 still permits explicit EXTERNAL-to-local ownership transfers for external-memory handoff. Thus this controlled A/B shows that adding those barriers to the existing per-frame import was insufficient; it does not prove that the external-memory path is otherwise synchronized correctly. The default two-pass path was not changed by this experiment.

A separate opt-in probe exported a read `sync_file` from each selected DMA-BUF immediately before Vulkan mapping. For seq 8/9, 17/18, and subsequent adjacent good/bad phases, the export ioctl succeeded and zero-time `poll` found the fence already signaled, including on every bad ninth phase. The three-second direct clip still had 120 black frames among 1,082 encoded frames. This rules out a *pending* implicit producer fence at that specific read point as the sole cause; it does not establish that the captured allocation or Vulkan image view contained valid pixels at that point. The probe used no CPU pixel access.

## Controlled two-pass path at 1440p360, pool 32

A repeatable harness (`tools/controlled_benchmark.py`) launched the full-screen 360 Hz plasma stimulus, waited for its first presentation feedback, recorded H.264 through `--conversion two-pass --pool 32 --async-depth 8` for 12 seconds, and decoded the saved GPU-drawn frame IDs offline. The stimulus presented 6,475 frames over 18.0032 seconds (359.657 FPS) with zero source ID gaps. The recorder reported 4,311 captured, submitted, encoded, and muxed frames, zero internal capture/packet drops, and a 75,009,963-byte MKV. Steady one-second captured/submitted/encoded rates were 357.816–357.946 FPS (mean 357.880); the encoder-utilization sampler reported 99% at each steady sample. The pool reached 32/32 occupied and logged 1,192 starvation periods totaling 1,285.63 ms. This is a near-360 result, but saturation leaves little margin.

The first approximately 36 recorded images show the full-screen stimulus moving from an initial offset to its final pixel origin. They contain valid visible IDs but do not fit the offline verifier's fixed sampling geometry. Skipping the first 50 decoded images leaves 4,261 analyzed frames with IDs 173–4,441 and **zero black, invalid, duplicate, or backward frames**. Eight source IDs are absent between adjacent saved frames over an ID span of 4,269 (0.1874%). The source presented every ID in that range. This is strong evidence of a readable, frame-ID-correct GPU-only recording at approximately 358 verified frames/s, with eight observed source-frame misses in the stable segment. A later known-color chart found that the default path swaps red and blue, so this does not establish full color correctness. A zero-miss sustained run and live GPU content identity remain desirable before treating the performance target as fully closed.

`ffprobe` read all 4,311 video packets from this MKV with strictly increasing source DTS (zero non-increasing pairs), and an offline FFmpeg decode completed successfully. FFmpeg's null output muxer emitted five same-DTS warnings after rescaling to its own timebase; those warnings do not describe the saved Matroska packet order. The harness now waits an extra 200 ms after first presentation for the full-screen geometry to settle, so later runs can validate the entire file without trimming startup frames.

The corrected shutdown path now drains completed capture frames before encoder flush, allowing captured/submitted/encoded/muxed totals to match in the controlled direct runs. Matching counters cannot detect pixel corruption, which is why offline image-ID checks remain mandatory.

## Matched two-pass pool comparison and a high-motion stress run

The benchmark harness waits for the first presentation and then allows 200 ms for the full-screen surface to settle. At the same plasma motion setting of 0.20, a 12-second H.264 recording with pool 24 captured, submitted, encoded, and muxed 4,267 frames. The 18-second source presented 6,479 consecutive IDs at 359.852 FPS. The entire saved file decoded with valid IDs 198–4,518, but 54 source IDs were missing between recorded frames (1.2497% of its ID span). There were no black, invalid, duplicate, or backward frames. The pool was full, with 3,048 starvation periods totaling 3,393.55 ms; steady one-second encoded telemetry averaged 354.909 FPS and encoder utilization was 99%.

The matched pool-48 run used the same 0.20 motion, 12-second recording, 18-second source, H.264, 50 Mbps, and encoder async depth 8. The source presented 6,478 consecutive IDs at 359.797 FPS. The recorder captured, submitted, encoded, and muxed **4,321 frames**, with zero internal drops and zero pool-starvation periods. Offline decoding recovered IDs **212–4,532**, exactly 4,321 consecutive source frames, with **zero missing IDs, black frames, invalid frames, duplicates, or backward transitions** across the whole recording. Its 75,192,710-byte MKV is at `/tmp/fluxrec-controlled-pool48-motion020-20260927.mkv` with a neighboring summary JSON and source/recorder/decoder logs. This is an objectively verified 1440p360 interval with consecutive readable source IDs and no black frames on the GPU-only path. A later known-color chart revealed a red/blue channel swap in this default two-pass conversion, so full image correctness remains open.

The pool-48 run does not yet prove unlimited sustained headroom. Its one-second encoded telemetry averaged 357.844 FPS, while the capture-pool occupancy rose from 17 to 41 of 48 slots over the sampled interval and the capture queue reached 32. That backlog can absorb a finite 12-second deficit without losing source IDs, but will eventually exhaust a fixed pool if the service-rate gap persists. Seven slots remained at its last sample, which would fill in roughly 3.2 more seconds if that slope continued—about 15 seconds from recording start. This is an extrapolation, not an observed exhaustion time. The high-motion run did reach full occupancy: its early samples rose by about 7.7 slots/s and the first full sample appeared around five seconds after recording began. Its 5.267 seconds of cumulative starvation over 20 seconds confirms that simply increasing the pool cannot sustain that workload indefinitely.

A different 20-second pool-48 run increased plasma motion from 0.20 to 1.0, so it is a stress test rather than a pool-size A/B. The source presented 8,559 consecutive IDs over 24.004 seconds, averaging 356.570 FPS with several slow intervals. Eighteen steady one-second encode samples averaged 352.518 FPS with 99% encoder utilization; one additional sample was a 236.667 FPS outlier. This shows that stronger motion and source-side rate variation still defeat zero-miss capture under the current two-pass encoder configuration.

## Capped-rate validation before capture-pacer precision fix

Four serial eight-second recordings used the same 0.20-motion 360 Hz source, two-pass conversion, a 48-slot capture pool, encoder async depth 8, 50 Mbps target, and a 200 ms source settle. The source presented about 359.1–359.6 consecutive IDs per second in every 14-second run, with zero source ID gaps. The requested FPS is a capture ceiling; source IDs intentionally skip when recording below 360 FPS. All saved packet streams had strictly increasing DTS.

| Codec and cap | Saved video frames | Measured video FPS | Black frames | Pool starvation | Decoder result |
| --- | ---: | ---: | ---: | ---: | --- |
| H.264 60 | 464 | 57.85 | 0 | 0 ms | All IDs valid; observed source-ID strides mostly 6, with some 7 |
| H.264 120 | 887 | 110.74 | 0 | 0 ms | All IDs valid; observed strides mostly 3, with some 4 |
| H.264 240 | 1,719 | 214.72 | 0 | 0 ms | All IDs valid; observed strides 1 or 2 |
| HEVC 120 | 888 | 110.90 | 27 | 0 ms | 861 valid IDs, no duplicates/backwards; 27 unknown transitions across black frames |

The near-identical H.264 and HEVC rates at the 120 cap, despite different encoder utilization (about 46% versus 90%), identify capture pacing as the rate limit in these capped tests. Inspection found that the worker rounded every next-request deadline up to a whole millisecond, then re-anchored the following deadline at the delayed request. This accumulated about 0.6–0.7 ms per frame; a nanosecond-resolution wait is being implemented. These are pre-fix measurements and must not be treated as the intended 60/120/240 rates.

HEVC's 27 black pictures appeared at decoded indexes 20, 53, and every 33 thereafter through 878, confirmed independently by FFmpeg black detection. An opt-in capture-slot sidecar mapped each black packet to a captured frame; the corresponding slot indexes cycled 4,5,6,7,0,1,2,3 across the active eight slots. The pool high-water was only 8 of 48, with no starvation or internal drops. Thus HEVC corruption is present even without pool exhaustion and is not confined to one capture allocation. The H.264 120-cap file, captured at nearly the same actual rate, was clean.

## Known-color chart reveals red/blue swap in default H.264 path

A GPU-drawn `colorchart` stimulus adds eight solid color bars, grayscale and RGB ramps, and a neutral checker, while retaining the moving visible frame ID. A four-second uncapped recording through the default two-pass H.264 path saved 1,441 readable, consecutive frame IDs at about 360 FPS, with no black or malformed-ID frames. ## GPU NV12 color-correction experiment and long-run regression

The source-side screenshot and earlier chart established that the default two-pass Vulkan path reversed red and blue. Hyprland 0.56.2 copies an `ext-image-copy-capture` frame from the monitor
mirror on output commit and ignores later commits while that copy is in
flight. The protocol allows only one frame object per session, so a commit
that arrives before the client can submit the next request is not captured.
That matches a skipped source ID. An extra commit of an unchanged mirror
matches the near-duplicate packet, after which the following source frame can
also be skipped.

Capture now opens three sessions and, when `presentation_time` reports that a
copy has started, arms exactly one other session. One commit is not copied
twice. A stale slot release can no longer free a newer lease: the slot stores
the lease sequence, and a queue-full drop no longer marks the slot free while
its lease still exists.
