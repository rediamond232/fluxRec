# Fluxrec

Fluxrec is an experimental native Wayland recorder for Hyprland and NVIDIA GPUs. The headless recorder defaults to NVENC; use `--backend vulkan` to select Vulkan Video. A fresh default H.264 run omitted backend, preset, coder, and async-depth options; startup selected NVENC P1/CAVLC at depth four, and the ten-second high-motion file decoded to 3,601 consecutive source IDs. The H.264 NVENC CAVLC route also completed a source-ID-verified 90-second high-motion run at a 50 Mbps VBR request, saving 32,392 consecutive decoded IDs with no starvation and pool high-water 15/48. The Vulkan Video H.264 path separately completed a source-verified 60-second run at 360.1 encoded FPS on an RTX 3090 Ti under low motion. NVENC also completed 60-second low-motion H.264 and HEVC recordings with 21,598 and 21,596 consecutive decoded source IDs, respectively, near the 359.979 Hz display cadence; the high-motion HEVC run passed 60 seconds. The revised PTS-based 60, 120, 240, and 360 FPS caps have passed controlled source-ID checks at their respective sampling rates. The default H.264 CAVLC path also passed a 20-second high-motion recording with audio and replay export. A 20-second fullscreen `vkgears` run captured 7,200 frames with unique GPU digests at the display cadence; this simple 3D demo is not game validation. A fullscreen Minecraft 1.21.11 practice-world capture saved 7,201 frames in 20 seconds; a separate digest run classified all 7,201 adjacent captures as unique. Sparse F3 samples do not quantify precise game-FPS impact. CS2 and indefinite high-motion headroom remain unproven. The UI exposes backend, NVENC preset, B-frame count, and separate per-backend async-depth settings.

The opt-in integrated CUDA EGL backend decoded 3,590 consecutive high-motion source IDs in a 10-second run. An earlier 60-second run encoded 21,596 frames but skipped source ID 821 between IDs 820 and 822. That miss, and a later 30-second duplicate-then-gap, came from Hyprland dropping output commits while a capture copy was still in flight. Capture now keeps one request armed on another session during that copy. Later 30-second and 60-second plasma recordings, including one with replay export, decoded exact source-ID sequences. Those runs do not prove the race can never recur.

The current NVENC pipeline keeps raw pixels on the GPU but copies converted NV12 from Vulkan to CUDA device memory. It has not met the original allocation-level zero-copy milestone. The [Vulkan/CUDA handle capability checks](docs/vulkan-cuda-memory-bridge.md) and [GL-owned DMA-BUF export probe](docs/gl-owned-dmabuf-export-probe.md) document the tested direct-memory alternatives and their limits on this machine.

An isolated desktop CUDA EGL probe completed a 60-second high-motion H.264 run on the RTX 3090 Ti through DMA-BUF → EGLImage → CUDA array → NVENC CUDA array input. It decoded 21,557 consecutive source IDs with zero black frames at 359.271 FPS over a 60.002-second capture window (60.762 seconds external wall time), using low-latency tuning, CAVLC, a 50 Mbps VBR request, and async depth 12. That diagnostic writes raw H.264 and remains separate from the production recorder.

The recorder now also has an opt-in integrated H.264 Matroska backend, selected with `--backend experimental-cuda-egl`. Its first production-binary smoke waited 1.5 seconds for fullscreen to settle, then passed all 13 fullscreen checks. Capture, submission, encode, and mux counts were each 721 with no drops or pool starvation. Offline decode found consecutive source IDs 729–1,449 with no black or invalid frames; the 2560×1440 H.264 MKV had BT.709 limited-range metadata and 721 packets with strictly increasing `PTS=DTS` and positive durations. Color-chart bar/ramp MAE was 0.70/0.63.

A follow-up five-second GOP-120 run passed 24/24 fullscreen checks. Capture, submission, encode, and mux counts were each 1,799 with no drops or starvation. Offline decode found consecutive IDs 704–2,502 with no black or invalid frames; `ffprobe` found 15 IDR keyframes at packet indexes 0, 120, …, 1,680. At the time of that run, periodic encoded-FPS telemetry underreported this backend; a later five-second check showed about 358–359 FPS in the periodic samples. NVIDIA documents `cuGraphicsEGLRegisterImage()` as Tegra-only, so this desktop behavior is empirical and does not prove allocation-level zero-copy or rule out driver-internal staging. The direct startup path no longer creates an FFmpeg Vulkan device. See the [probe details](tools/nvenc_egl_cudaarray_probe.md) and [measurement log](docs/measurements.md).

On high-motion plasma, the integrated backend encoded 3,590 frames in the requested 10 seconds; all 3,590 decoded source IDs were consecutive and valid, with no internal drops or pool starvation. The original 60-second run encoded 21,596 frames, about 359.9 per requested second, but the decoded file skipped source ID 821 between 820 and 822 at frame 102. All decoded pictures were otherwise valid, unique, and forward; therefore that 60-second test is not drop-free despite zero reported internal drops. Both runs used a 120-frame IDR interval. A later 60-second run after the overlapped-capture change decoded IDs 705–22,262 with no gaps. Direct replay-only, recording-plus-replay, and a two-track audio recording have since been checked. Direct HEVC on the same path decoded exact high-motion source IDs through 60 seconds at about 359.3 FPS with Main-profile BT.709 limited metadata. Qt settings expose this backend with its actual limits and do not call it allocation-level zero-copy. A fullscreen `vkgears` vsync run and one authenticated Minecraft practice-world recording held display cadence; the Minecraft server logged a pause near the end of that take, the game does not paint source IDs, and CS2 remains unmeasured.

The project is under active construction. A source-patched private FFmpeg runtime fixes the red/blue swap in the two-pass converter and synchronizes the HEVC Vulkan scale pass; CMake selects it through the recorder's embedded runtime path. The faster native-size converter remains experimental after producing a black frame every ninth output in its tested configuration. Replay saving, two-track desktop/microphone capture, and the native Qt UI have working initial implementations; high-motion replay-only exports passed with 60- and 120-second histories. The 120-second export decoded 43,252 consecutive video IDs and two AAC tracks with strict DTS and zero drops. See [measurements](docs/measurements.md) for capture counts and known limits.

## Build

On Arch Linux, the current prototype uses CMake, Ninja, a C++23 compiler, Wayland client and protocols, Vulkan, GBM, and FFmpeg development libraries. The recorder requires source-patched FFmpeg 9.0.2 `libavutil`, `libavfilter`, and `libswscale`; the build helper fetches hash-pinned source and AMF headers, builds the libraries under ignored `.deps/`, and does not modify system libraries. Modules may have additional dependencies listed in their directories.

```sh
cmake -S . -B build-release -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo \
  -DFLUXREC_TELEMETRY_BUILD_TESTS=ON
cmake --build build-release
ctest --test-dir build-release --output-on-failure
```

On a clean checkout, the default CMake build creates the private libraries before linking the recorder. To prepare them separately, run `./scripts/build-ffmpeg-bgra-b8.sh`. For an offline build, provide verified cached FFmpeg, AMF-header, and nv-codec-header archives through `FLUXREC_FFMPEG_ARCHIVE`, `FLUXREC_AMF_HEADERS_ARCHIVE`, and `FLUXREC_FFNVCODEC_ARCHIVE`. The helper checks each SHA-256 before extracting or compiling. CMake validates the three-library runtime and checks that the built recorder resolves them through its `DT_RPATH`, including when the Qt UI launches the recorder. See [private runtime build details](patches/README.md).

## Headless recording

On the target Hyprland/NVIDIA system:

```sh
./build-release/engine/fluxrec-record --output "$HOME/Videos/fluxrec-test.mkv" \
  --display DP-1 --seconds 10 --codec h264 --bitrate-bps 50000000 \
  --pool 48 --conversion two-pass --encoder-tune default
```

The recorder emits periodic JSON telemetry on stdout and a final count summary on stderr. Use `--conversion two-pass` with the default NVENC backend for validated recordings; `--backend experimental-cuda-egl` selects the separate opt-in route. Its checked evidence includes H.264 and HEVC high-motion source-ID runs, replay, and two-track audio; it is an application-level direct GPU path, not allocation-level zero-copy, and `nvEncLockBitstream` still has no safe in-process deadline on this driver. A direct pool below 16 prints a startup warning: five-second motion-1 checks with 4 and 8 buffers skipped source IDs while `capture_dropped` stayed 0, and the default 16-buffer pool stayed exact. A positive container frame rate is not evidence of unique source frames; controlled 360 Hz measurements and offline decoded-frame ID checks are documented separately. The source-ID decoder defaults to luma threshold 100; use `--threshold` (or the harness's `--decode-threshold`) to calibrate another compressed output path because segment luma can shift near the decision boundary.

`--bitrate-bps` accepts 1,000,000–500,000,000 bits/s; `--qp 0..51` opts into experimental constant-QP mode and cannot be combined with an explicit bitrate. `--gop` sets the keyframe interval in frames. `--resolution WIDTHxHEIGHT` requests an even output size from 4×4 through 16384×16384; the Vulkan conversion scales to that size, and the GPU encoder still validates whether the selected device and codec support it. The mux header uses the encoded output dimensions. `--max-fps 0|60|120|240|360` limits admitted output frames from compositor presentation timestamps with a two-frame burst allowance (`0` is uncapped); at 60, 120, and 240 FPS it also paces capture requests, while 360 FPS requests remain immediate. It preserves compositor timestamps and does not synthesize a constant encoded frame rate. NVENC is the CLI default and uses the NVENC tune mapping for `--encoder-tune default|ll|ull|hq`; the default maps to low-latency tuning. Use `--backend vulkan` to select Vulkan Video, whose tune option maps to FFmpeg's Vulkan encoder modes. `--nvenc-preset p1..p7` selects an NVENC preset. Omitting `--async-depth` with NVENC selects the validated depth four and synchronizes the Vulkan scale path; Vulkan Video defaults to depth eight. The `FLUXREC_GPU_ENCODER_BACKEND` environment setting remains available for diagnostics when `--backend` is omitted. H.264 defaults to NVENC `cavlc`; `--h264-coder cabac` selects NVENC `cabac` explicitly. The capture pool defaults to 48 buffers and remains configurable with `--pool 2..64`.

The default NVENC backend copies Vulkan NV12 planes into CUDA pitch-linear frames with a
GPU-to-GPU transfer; the path is not allocation-level zero-copy. Source inspection
and a short syscall trace found no CPU mapping, read, or copy call on the tested
DMA-BUF descriptors, but cannot rule out every user-space load or driver-internal
stage. A three-second
H.264 desktop smoke with an eight-frame NVENC delay encoded and decoded successfully
on the RTX 3090 Ti at 1,044 frames in three seconds with no pool starvation; its
throughput was below the adjacent Vulkan Video run. Controlled 360 Hz
source-ID runs subsequently found periodic black pictures in both H.264 and
HEVC NVENC output at async depth eight. Increasing the in-flight depth to
sixteen left one black picture in an eight-second numbered-source check.
Depth four with the synchronized Vulkan filter then passed 60-second
production-binary H.264 and HEVC source-ID runs without black output, gaps,
drops, or pool starvation. An entropy-coder comparison found that the prior NVENC default resolved to CABAC and missed 41 source IDs in a 20-second high-motion run, while explicit CAVLC stayed clean for 90 seconds at the same 50 Mbps VBR request. The recorder now passes its default VLC choice to NVENC as CAVLC; the rebuilt default passed a 20-second high-motion recording with audio and replay export. The VBR request measured about 83 Mbps in the 90-second CAVLC file. CS2 capture and sustained headroom in more demanding games remain unvalidated. H.264 is the validated default codec; HEVC has passed the listed source-ID checks but remains less broadly validated, and HEVC B-frame throughput fell below 360 FPS. See
[NVENC route details](gpu/README.md).

`--b-frames 0..4` controls optional NVENC frame reordering; zero is the default and the setting is rejected for Vulkan Video. H.264 NVENC with two B-frames passed an eight-second source-ID recording and replay export with two AAC tracks. HEVC NVENC with two B-frames decoded correctly but fell below 360 FPS in a twelve-second test, so the longer 360 FPS claims above apply to the default zero-B-frame mode.

An isolated FFmpeg diagnostic can collect host wall spans around `nvEncEncodePicture` and the blocking `nvEncLockBitstream` call. With the diagnostic private codec loaded, set `FLUXREC_FF_NVENC_API_TIMING=1`; JSON reports the two call timings and recent pairs joined by frame PTS, including reordered output. These measurements can include driver waiting and are not NVENC hardware durations. The default runtime does not include the patched codec. See [the private FFmpeg timing notes](patches/README.md#source-patched-ffmpeg-vulkan-runtime).

The [NVENC input API audit proxy](tools/nvenc_input_audit/README.md) passed on the loaded system codec: one encoder initialization registered four CUDA device-pointer resources, with zero non-CUDA registrations and zero software input-buffer create or lock calls. This confirms the NVENC input branch for those sessions; it does not audit the preceding Vulkan/CUDA stages or driver-internal copies.

Desktop and microphone capture can be enabled together with `--audio on`. It starts two PipeWire sources and writes two AAC tracks. Audio is off by default so a missing microphone does not block a video-only recording. `--replay-seconds 30` keeps compressed video and, when enabled, audio packets in a bounded memory ring during recording; send `save_replay /absolute/path.mkv` to the recorder's standard input to export the selected A/V history asynchronously. The ring budget is estimated from the requested history plus keyframe preroll at `max(120 Mbps, 2 × requested bitrate)`, and is clamped between 512 MiB and 2 GiB. In-flight exports have a separate snapshot budget equal to the ring budget, so replay payload memory is bounded by 4 GiB and can exceed the ring budget while a save is active. The buffers allocate lazily. Longer custom histories that exceed the byte cap report `insufficient_history` when saved instead of silently exporting a shorter clip. `--replay-only --replay-seconds 30 --audio on` captures the same sources without creating the primary recording file.

For content-identity diagnostics, add `--verify-frame-ids`. It hashes every visible RGB pixel on the GPU before conversion, reads back only a 16-byte digest, and writes one JSON record per completed digest to stderr with capture sequence, PTS, and adjacent-frame classification. The regular telemetry JSON then reports `frames.unique`, `frames.duplicated`, `frames.identity_checked`, `frames.identity_skipped`, `frames.identity_unclassified`, `fps.unique`, and the `frame_identity_gpu` timing. This extra full-frame compute pass reads about 14.7 MB per 2560×1440 frame (about 5.3 GB/s at 360 FPS), plus per-frame JSON logging; keep the option off for throughput measurements. See [frame identity details](gpu/shaders/frame_identity.md).

`--verify-frame-ids-source-only` is a diagnostic variant that submits just the source-reading compute pass and reports sequence/PTS/GPU timing records without hashing output, reducing, or reading back a digest. It leaves unique and duplicate telemetry absent. Use it to isolate source-read GPU work from the reduction and digest-readback work.

`--verify-frame-ids-unrelated N` runs a same-grid math-only Vulkan workload with no imported image descriptor or image access, then signals the frame timeline before conversion. `N` controls 1–64 rounds of integer mixing per pixel so the workload can be calibrated against the source-read pass. It does not produce identity hashes or unique/duplicate counts.

## Native UI

The Qt 6 Widgets shell and the recorder are one program, `build-root/engine/fluxrec`. Running it opens the UI. Recording starts that same binary again with `--engine`, so capture stays a separate process. `build-root/engine/fluxrec-record` and `build-root/ui/fluxrec-ui` are links to it. A blank recorder path in Settings uses this program. The UI selects the visually verified two-pass converter and can receive a downscaled GPU-produced preview without mapping full-resolution capture pixels to the CPU. In a five-second UI pause test, the separate recorder kept writing and produced 3,453 consecutive source IDs; long-run preview-release behavior still needs validation.

## Engineering constraints

- Captured raw video pixels remain on the GPU during normal recording. There is no silent CPU framebuffer fallback.
- Wayland capture events feed a bounded frame pool, but the recorder loop calls `encoder.submit()` synchronously for each frame. NVENC's two-pass Vulkan path waits on the host after both scale stages; removing either wait produced black frames in the ablation test. Once encoded packets emerge, a nonblocking bounded packet router separates recording from replay/mux work; mux and disk writing use their own worker, and audio forwarding, replay export, and the UI run independently.
- Report actual captured, unique, encoded, muxed, dropped, and duplicated frame counts. Container timestamps alone are not evidence of frame rate.
- Replay history stores compressed packets in RAM.

The [project objective](docs/objective.md) tracks the full requested scope. Architecture and measurement notes will be recorded as the engine is implemented and validated.
