# Fluxrec Qt shell

The UI is a native Qt 6 Widgets application that stays separate from capture and encoding internals. `RecorderBackend` is the interface widgets consume; `ProcessRecorderBackend` adapts the headless `fluxrec-record` command to it with `QProcess` and JSONL telemetry.

Build it alone from the repository root:

```sh
cmake -S ui -B build-ui -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo
cmake --build build-ui -j
QT_QPA_PLATFORM=offscreen ./build-ui/fluxrec-ui --smoke
```

The root CMake build adds this directory after defining `fluxrec-record`. The UI target only needs Qt 6 Widgets and Python 3 for its design-token drift check; it does not link the engine libraries. With `BUILD_TESTING` enabled, CTest runs an offscreen `fluxrec_ui_smoke` that creates and closes the window without launching the recorder.

## Recorder process contract

The adapter searches `PATH` for `fluxrec-record` and lets Settings override the executable path. It passes discrete arguments, including `--until-signal`, selected Wayland output, `--conversion two-pass`, codec, `--backend vulkan|nvenc`, NVENC-only `--nvenc-preset p1..p7` and `--b-frames 0..4`, rate control, GOP interval, `--max-fps`, optional output resolution, frame-pool size, encoder async depth, the saved `--audio on|off` setting plus one `--audio-track` group per effective track when audio is on, optional `--verify-frame-ids`, replay history, and an absolute MKV path. The identity diagnostic setting is persisted as `recording/verifyFrameIds`, defaults off, and applies to both standard and replay-only sessions. It hashes each captured RGB image on the GPU, reads back a 16-byte digest, and writes one stderr record per completed digest. At 2560 × 1440 and 360 FPS, the estimated source-image read traffic is about 5.3 GB/s; this is a calculated traffic estimate, not a measured throughput cost. The diagnostic adds GPU work and synchronization, so enabled runs may have lower throughput. Statistics shows unique/duplicated frames and checked/skipped/unclassified coverage; absent coverage is shown as “Not reported,” not zero. NVIDIA NVENC is the default backend for fresh settings; Vulkan Video remains selectable. A previously saved backend choice remains selected. Settings keep async-depth values separately: Vulkan Video defaults to 8, while NVENC defaults to 4. NVENC H.264 and HEVC each passed a 60-second low-motion source-ID check with the synchronized scale path, async depth 4, and a 48-buffer pool. Controlled H.264 and HEVC runs at NVENC depth 8 produced periodic black output; Settings recommends depth 4 for normal recordings. Separate high-motion NVENC checks passed: explicit CAVLC H.264 at a 50 Mbps VBR request produced 32,392 consecutive source IDs in 90 seconds with pool high-water 15/48, and HEVC produced 21,599 consecutive IDs in 60 seconds. The rebuilt default CAVLC path also passed a 20-second high-motion recording with two audio tracks and a source-verified replay export. A separate bounded 20-second fullscreen Minecraft practice-world capture saved 7,201 H.264 NVENC frames at about 360 FPS, and an opt-in digest run classified all 7,201 adjacent images as unique. CS2, sustained headroom in more demanding games, alternate presets, and other hardware/configurations remain unvalidated. Bitrate mode remains the default at a 50 Mbps average target. Settings labels the control “Average bitrate target” and explains that it is not a maximum bitrate or file-size limit; Statistics shows the observed output bitrate. In one high-motion H.264 NVENC CAVLC VBR recording, the 50 Mbps target produced about 83 Mbps output bitrate. Experimental CQP mode passes `--qp N` without a bitrate option; QP is bounded from 0 to 51 for this 8-bit NV12 path, with 28 as the saved default. H.264 QP 28 was checked on one NVIDIA RTX 3090 Ti setup: all 1,080 recorded images decoded as valid/nonblack, though one adjacent source ID was skipped near startup; the color chart had mean bar MAE 0.54 and maximum channel error 2. The source presented consecutive IDs. Other QP values, codecs, drivers, and device combinations remain experimental. H.264 uses VLC/CAVLC by default for the measured throughput headroom; CABAC remains available from the command line. FPS choices cap frames admitted to the recording pipeline using compositor presentation timestamps; `0` is uncapped compositor/display cadence, and a cap does not guarantee an output rate. A paired 8-second H.264 test at the 360 FPS PTS cap decoded 2,881 consecutive source IDs at about 360 FPS with no black, invalid, missing, or dropped frames. The current PTS bucket and request pacing also passed guarded ten-second NVENC checks at 60, 120, and 240 FPS with valid, nonblack sampled source IDs, no internal drops or pool starvation, and mean steady encode rates of 59.7, 119.4, and 236.6 FPS. Resolution defaults to native capture; selected sizes use the two-pass GPU conversion path. The UI pins two-pass conversion because the direct native-size path still has a recurring black-frame fault. HEVC requires explicit acknowledgement and remains experimental. A 10-second 1440p HEVC test with Vulkan Video at a 120 FPS cap produced 1,192 valid, nonblack frames at about 119 FPS; the NVENC check above covers one 60-second workload. Longer high-motion Vulkan sessions, game capture, alternate presets, and other configurations remain unvalidated. The UI reads newline-delimited JSON snapshots from stdout (`capture`, `frames`, `fps`, `queues`, `storage`, `timings_ns`, `system`, `audio`, and `replay`) and diagnostic text from stderr. Statistics separates frames delivered to processing from Wayland capture completions and admitted frames; rate-limited frames are labeled as intentionally withheld by the FPS cap, not as processing errors. Null or absent measurements stay unavailable; the last snapshot is marked stale after three seconds without a report. Standard recording stops with SIGINT, waits up to eight seconds for the recorder to drain and exit, and reports success only after a clean exit and a non-empty output file.

The opt-in `--backend experimental-cuda-egl` launch omits `--conversion`, `--preview-socket`, `--verify-frame-ids`, and `--nvenc-preset`. It passes `--b-frames 0`, a separate capture pool of 3–16 (default 16), and a separate async depth of 1–16 (default 12). Bitrate mode passes `--bitrate-mbps`. Experimental constant QP passes `--qp N` and omits the bitrate argument; that direct-path mode has not been live-checked. H.264 CAVLC and HEVC Main are both selectable; HEVC still requires the experimental acknowledgement. Settings describes this as an application-level direct GPU path and does not call it allocation-level zero-copy. The workbench toolbar and signal rail follow that choice: Direct CUDA EGL shows WAYLAND › EGL › NVENC › MATROSKA and an explicit unused preview, instead of the Vulkan two-pass rail. GPU preview and the frame-identity digest are unavailable on this backend.

Replay-buffer start and stop use `start_replay\n` and `stop_replay\n`; the engine acknowledges each state change. When idle with replay history configured, Start replay-only session launches `fluxrec-record --replay-only --replay-seconds N --until-signal --audio on|off` using the saved Audio capture setting, plus one `--audio-track` group per effective track when audio is on, without a primary output path. When enabled, each effective track’s packets are retained as synchronized replay tracks and included in Save replay. Stop sends `stop\n` and waits for clean process exit; no primary file is expected. During either workflow, Save replay sends `save_replay /absolute/path.mkv\n` to recorder stdin when an enabled ring is reported. The path remainder may contain spaces; control characters are rejected by the process protocol. A `replay_queued` event updates pending status; `replay_saved` (`path`, `ok`, and optional `message`) provides the final success or failure.

NVENC exposes an opt-in B-frame count from 0 to 4, saved as `recording/nvencBFrames`. It defaults to 0; the control is visible and enabled only when NVENC is selected, and the value is passed for both recording and replay-only sessions. The GOP must be at least the B-frame count plus two frames. Vulkan Video currently rejects nonzero B-frame requests. A nonzero NVENC value disables the explicit low-latency and zero-reorder flags, adds decode/presentation reordering, and requires device support. CPU replay-export coverage exercises reordered H.264 packets with separate PTS/DTS and synchronized audio. A live eight-second H.264 NVENC B-frame-2 recording plus replay saved consecutive numbered source IDs in both files with two AAC tracks. A twelve-second HEVC B-frame-2 run decoded correctly but fell to about 307 steady FPS, filled the pool, and missed source IDs. Use 0 for the longest validated 360 FPS intervals; B-frame performance depends on codec and workload.

The preview path receives a downscaled GPU-produced DMA-BUF image; full-resolution capture pixels are not mapped to the UI or copied to the CPU for preview. Scenes & Sources stores named, local capture profiles. On the Qt Wayland platform, the output picker lists `QScreen` names, refreshes on demand and after screen changes, and marks an unset or no-longer-reported output unavailable. Manual entry appears for an unset or unavailable output, or when the current Qt platform cannot verify names; the recorder still confirms that name when it starts. Each profile selects exactly one output; selecting a scene changes the next session's `--display` target and does not composite outputs. Scene selection and profile edits—including the selected output field in Settings—are disabled while recording or replay-only capture is starting, active, or stopping. Other Settings changes apply to the next session. The audio mixer uses only engine telemetry and typed control acknowledgements; no sample meters or capture values are synthesized.
